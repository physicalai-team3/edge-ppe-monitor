## 핵심 설계 결정

1. **3단 필터.** ESP32는 "사람이 있나?"만 본다(가벼운 모델). Pi는 "보호구를 썼나?"를 본다(무거운 모델). 클라우드는 **위반만** 받는다. 단계마다 데이터가 줄어서 통신비·저장비가 거의 들지 않는다.
2. **ESP32 → Pi는 HTTP 한 번.** 사진(수십 KB)은 MQTT보다 HTTP POST가 다루기 쉽다. 응답으로 판정 결과를 바로 돌려받아 ESP32 LED로 보여준다.
3. **Pi 안은 컨테이너 2개.** 받는 일·판정·업로드(`gateway`)와 딥러닝 추론(`detector`)을 나눴다. 모델을 바꾸거나 `mock`으로 바꿔 끼워도 `gateway`는 그대로다.
4. **클라우드가 끊겨도 위반은 잃지 않는다.** `gateway`는 위반을 먼저 Pi 디스크(`outbox`)에 저장하고, 백그라운드에서 Supabase로 올린다. 위반 ID를 Pi가 만들어서 재시도해도 중복 행이 생기지 않는다.
5. **비밀 키는 Pi에만.** Supabase 쓰기 키(secret)는 Pi `.env`에만 있다. 웹은 읽기 전용 키(publishable) + RLS로 조회만 한다.
6. **가짜로 바꿔 끼우기.** 보드가 없으면 `cam-sim`, 모델이 없으면 `DETECTOR_MODE=mock`, Pi가 없으면 `cloud-seed`로 각자 혼자 개발할 수 있다.
